# 開発ワークフロー

ブランチ・コミット・PR を一貫して扱うための手順書。

## 目的

- [Git Flow](https://nvie.com/posts/a-successful-git-branching-model/) に沿った `main` / `dev` / 作業ブランチの役割を守る。
- 作業の起点・マージ先を迷わず、レビュー可能な単位で変更を積み上げる。
- ブランチ名・コミットメッセージ・PR 説明の分類を揃え、エージェントと人間の共同作業をしやすくする。

## ブランチ構成

永続ブランチ（Git Flow のコアブランチ）:

| ブランチ | 役割                                             |
| -------- | ------------------------------------------------ |
| `main`   | 本番相当。リリース済み・安定した履歴を保持する。 |
| `dev`    | 開発統合先。次に `main` へ載せる変更を集約する。 |

短命ブランチ（作業ブランチ）:

- 通常の機能・修正・ドキュメント等は **`dev` から分岐**し、完了後 **`dev` にマージ**する（Git Flow の feature ブランチ相当）。
- `dev` や `feature` に対するバグ修正は `bugfix/` を用いる。
- 本番への緊急修正は **`main`（またはリリース中のタグ）から分岐**する `hotfix/` を用い、修正後は **`main` と `dev` の両方**へ反映する（Git Flow の hotfix ブランチ相当）。
- リリース準備用の `release/` ブランチは、リリース運用を開始するまで必須ではない。必要になったら人間が方針を決める。

### 親作業ブランチと子作業ブランチ（チーム並行作業）

複数人で同一の大きな変更を進めるとき、**親作業ブランチ**（統合ブランチ）の下に **子作業ブランチ** を切る。

```text
dev
  └── feature/user-auth             … 親（機能単位の統合先）
        ├── feature/user-auth-login-ui
        └── feature/user-auth-session-api
```

| 種別           | 役割                                                                 | 分岐元                            | マージ先                                         |
| -------------- | -------------------------------------------------------------------- | --------------------------------- | ------------------------------------------------ |
| 親作業ブランチ | 1つの機能・テーマ全体の統合先。子の変更を集約してから `dev` へ載せる | `dev`（または合意された親の起点） | 原則 `dev`                                       |
| 子作業ブランチ | 親の一部を担当者ごと・タスクごとに分割した作業単位                   | **親作業ブランチ**                | **親作業ブランチ**（`dev` へは直接マージしない） |

運用の要点:

- 親は **最初にリモートで作成**し、チームの統合基点として共有する。
- 子は親から分岐し、完了したら **親への PR** で取り込む。親が揃ってから **親 → `dev` の PR** を出す。
- 子ブランチの寿命は短く保ち、マージ後は削除する（GitHub/Bitbucket等のリモートでも同様）。
- 階層は **親 + 子の2段**までとする。孫ブランチ（子のさらに下）は作らない。分割が足りない場合は、親を別テーマに分けるか、子の粒度を見直す。
- Gitのref名はパスのように扱われるため、既存ブランチ名をそのままディレクトリ名にする子ブランチは作らない。例えば `feature/phase1` が存在する場合、`feature/phase1/project-foundation` は作れない。
- `hotfix/` は本番緊急用のため、親子階層には使わない。

エージェントは `main` / `dev` に直接コミットしない。
子作業ブランチから `dev` へ直接 PR・マージしない（明示的な例外指示がある場合を除く）。

## 作業開始手順

### 単独作業（親子なし）

1. **リモートで作業ブランチを作成する**（GitHub/Bitbucket等 上）。ローカルのみでブランチを切る運用は他者が作業の存在・状況を把握しづらくなるため、この手順を遵守する。
2. ローカルで `dev`（または hotfix の場合は `main`）を最新化し、作業ブランチをチェックアウトする。
3. 実装・テスト・`./scripts/agent-check.sh`（または対象に応じた検証）を行う。
4. 作業中は **定期的にリモートの作業ブランチへ push** する。
5. **Pull Request（PR）** を作成し、レビューを経てマージする。
6. 通常変更は **`dev` にマージ**する。リリースタイミングで人間が **`dev` → `main`** の反映（マージコミット等）を行う。

### チーム並行作業（親子あり）

1. 担当リードまたは人間が、**リモートで親作業ブランチ**を `dev` から作成する（命名は下記「親子ブランチの命名」）。
2. 各担当者は **リモートで子作業ブランチ**を親から作成する。
3. 作業前に親を `git pull`（または fetch + merge/rebase）で最新化してから、子をチェックアウトする。親に他者のマージが入ったら、子側でも定期的に親を取り込む。
4. 子の作業が完了したら、**マージ先は親**の PR を作成する。検証結果は子 PR に記載する。
5. 親に必要な子が揃い、親ブランチ全体の検証が終わったら、**マージ先は `dev`** の PR を作成する。
6. リリース反映は従来どおり、人間が **`dev` → `main`** を行う。

作業開始前に、現在のブランチ名が命名規約に合っているか、親子関係と PR のマージ先が正しいかを確認する。合わない場合は、実装・コミット提案の前にユーザーへ確認する。

## 作業ブランチの命名規約

作業ブランチ名は、作業内容がひと目で分かる短く説明的な名前にする。
[Git Flow](https://nvie.com/posts/a-successful-git-branching-model/) でも、feature ブランチは「何のためのブランチか」が分かる名前にすることが前提になっている。

### 命名規約の変更（2026-06-02）

**2026-06-02 まで**はブランチ名に `yyyyMMdd` を付ける運用だった。**2026-06-02 以降**は日付を付けない。

変更理由:

- 日付の意味（作成日・親の開始日・子の作業開始日など）をチームで一貫して定義できていなかった。
- 親子ブランチでは、子の実際の作業開始が親の日付から離れると、名前上の日付が実態と食い違う。
- [Git Flow](https://nvie.com/posts/a-successful-git-branching-model/) や [Bitbucket の branching model](https://support.atlassian.com/bitbucket-cloud/docs/configure-a-projects-branching-model/) のような業界標準に沿った形（`prefix` + 説明、必要なら issue ID）に寄せ、独自ルールを最小限にする。

**既存ブランチ**: `feature/20260526-phase1` のように日付付きの名前がリモートに残っていてもよい。新規作成・リネーム時は本節の日付なし形式に従う。エージェントは日付なし形式を正とし、日付付き名を新規に提案しない。

基本形:

```text
<prefix>/<short-description>
```

Issue 番号やチケット番号がある場合:

```text
<prefix>/<issue-id>-<short-description>
```

例:

```text
feature/add-contact-form
bugfix/123-header-layout-bug
perf/public-page-load-time
docs/update-branching-strategy
hotfix/critical-api-error
```

### 親子ブランチの命名

親・子とも **同じ prefix** を用い、子は親の短い識別子をハイフン区切りのプレフィックスとして続ける。

親（統合ブランチ）: 作業ブランチ基本形と同じ。ただし必要に応じて `<short-description>` を機能単位やイシュー単位など、単独の場合よりは若干広めにつけることもある。

子（親から分岐する作業単位。`/` ではなく `-` で親識別子と子の説明をつなぐ）:

```text
<prefix>/<parent-short-description>-<child-short-description>
<prefix>/<parent-short-description>-<issue-id>-<child-short-description>
```

例:

```text
feature/user-auth
feature/user-auth-login-ui
feature/user-auth-42-session-api
bugfix/123-checkout-flow-124-payment-validation
```

ルール:

- 子の `<child-short-description>` は、親全体ではなく **その子ブランチの担当範囲**が分かる短い名前にする。
- 親の名前を変えない。親のリネームが必要なときは、人間が影響範囲（既存の子ブランチ・オープン PR）を確認してから行う。
- 子の prefix を親と別種別（例: 親が `feature/` で子が `bugfix/`）にしない。不具合修正が親機能の一部なら、子も `feature/` の配下とし、コミットメッセージの `type` で修正であることを示す。
- 親ブランチ名を完全一致の接頭辞にして `/` で子を作らない。`feature/phase1` の子は `feature/phase1-project-foundation` のようにする。

ブランチ名に使う文字は、小文字英数字、ハイフン、スラッシュを基本とする。
[`git-check-ref-format`](https://git-scm.com/docs/git-check-ref-format) で問題になる文字（空白、`..`、`~`、`^`、`:` など）は使わない。スラッシュはprefix直後の区切りにとどめ、親子関係の表現にはハイフンを使う。

### prefix の付け方

prefix は作業ブランチで行う作業の種類を表す。
[Atlassian / Bitbucket の branching model](https://support.atlassian.com/bitbucket-cloud/docs/configure-a-projects-branching-model/) でも、`feature` / `release` / `bugfix` / `hotfix` など種別を prefix で識別する運用が紹介されている。

このプロジェクトでは、次の prefix を用いる。

| prefix      | 用途                                                         | 対応する主なcommit type |
| ----------- | ------------------------------------------------------------ | ----------------------- |
| `feature/`  | 新機能追加（UIコンポーネントやUX更新含む）                   | `feat`                  |
| `bugfix/`   | 開発中または未リリース機能の不具合修正                       | `fix`                   |
| `hotfix/`   | 本番環境への緊急修正（分岐元・マージ先は上記 hotfix 運用）   | `fix`                   |
| `perf/`     | 表示速度、処理速度、転送量などのパフォーマンス改善           | `perf`                  |
| `refactor/` | 外部仕様を変えない内部構造の整理                             | `refactor`              |
| `docs/`     | ドキュメントのみの追加・修正                                 | `docs`                  |
| `test/`     | テストの追加・修正                                           | `test`                  |
| `chore/`    | UI文言のみの更新、依存更新、設定変更、開発補助などの保守作業 | `chore`                 |

ブランチprefixはGit FlowとBitbucketのbranching modelに合わせ、コミットメッセージは [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) のtypeに合わせる。

## コミットメッセージ規約

[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) を参考に、変更種別が分かる prefix を付ける。

基本形:

```text
<type>: <変更内容の要約>
```

要約は **日本語** で書く。

例:

```text
feat: お問い合わせフォームを追加する
fix: ヘッダーのSP表示崩れを修正する
perf: 公開ページの初期表示を改善する
docs: ブランチ戦略の説明を更新する
```

主に利用する `type` は、ブランチ prefix と同じく次のとおり。

| type       | 用途                                                         |
| ---------- | ------------------------------------------------------------ |
| `feat`     | 新機能追加（UIコンポーネントやUX更新含む）                   |
| `fix`      | 不具合修正                                                   |
| `perf`     | パフォーマンス改善                                           |
| `refactor` | 外部仕様を変えない内部構造の整理                             |
| `docs`     | ドキュメントのみの追加・修正                                 |
| `test`     | テストの追加・修正                                           |
| `chore`    | UI文言のみの更新、依存更新、設定変更、開発補助などの保守作業 |

## Pull Request 作成ルール

- **単独の作業ブランチ**: マージ先は原則 **`dev`**。
- **子作業ブランチ**: マージ先は **親作業ブランチ**。PR タイトル・説明に、親ブランチ名と担当範囲を書く。
- **親作業ブランチ**（子の統合後）: マージ先は **`dev`**。PR 説明に、取り込んだ子 PR の一覧または概要を書く。
- **`hotfix/`**: **`main`（および `dev`）** への反映方針を PR 説明に明記する。親子階層は使わない。

PR作成前に、破壊的Git操作、ファイル削除、大量リネーム、DB migration、secrets、外部送信先、認証・認可、実売買系に触る変更が含まれていないかを確認する。含まれる場合はPR作成前に明示的な人間承認を得る。

<!-- PRの構成はもう少し練る（ブランチの `prefix` ごとに定義する） -->

- PR 説明には次を含める。
  - **変更概要**（何をなぜ変えたか）
  - **検証結果**（実行したコマンドと結果）
  - **影響範囲**（触ったモジュール・設定・ドキュメント）
  - **未対応事項**（意図的に残した課題、人間確認が必要な点）
  - **Safety impact**（破壊的操作、secrets、認証・認可、外部送信先など重大領域を触ったか）
  - **Human approval required**（人間承認が必要だったか、承認済みか）
  - **Checks run**（`./scripts/agent-check.sh` など実行した検証）
- レビュー指摘への対応は、同じ作業ブランチにコミットして push する。

PR の種類ごとの詳細は次のとおり。

| PR の種類      | マージ元（source） | マージ先（destination） | テンプレート                                         |
| -------------- | ------------------ | ----------------------- | ---------------------------------------------------- |
| 単独作業       | 作業ブランチ       | `dev`                   | [PRテンプレート（共通）](#prテンプレート共通)        |
| 子 → 親        | 子作業ブランチ     | 親作業ブランチ          | [PRテンプレート（共通）](#prテンプレート共通)        |
| **親 → `dev`** | 親作業ブランチ     | `dev`                   | [PRテンプレート（親 → dev）](#prテンプレート親--dev) |
| `hotfix/`      | `hotfix/` ブランチ | `main` / `dev`          | 共通 + 反映方針を明記                                |

作業用の長文ドラフトはローカルの Git 管理外ディレクトリに置いてもよい（GitHub/Bitbucket等 本文への貼り付け用）。正本の手順は本ファイルとする。エージェントは Git 管理外ディレクトリのファイルをコミットに含めてはならず、`git add -f` で強制追加することも禁止する。

### 子作業ブランチ → 親作業ブランチ

- GitHub/Bitbucket等 で **source = 子**、**destination = 親** の PR を作る。
- 比較範囲は **`親...子`**（three-dot）。例: `feature/phase1...feature/phase1-project-foundation`
- PR には **子ブランチの担当範囲だけ**を書く。親全体の完了宣言はしない。
- マージ後、子ブランチは削除する（ローカル・リモートとも、チームで合意した場合）。
- 説明文は [PRテンプレート（共通）](#prテンプレート共通) を使い、`Merge target` に親ブランチ名を明記する。

### 親作業ブランチ → dev

親ブランチは **複数の子 PR が順不同・並行でマージされる統合先** である。親 → `dev` の PR は、「その時点で `dev` に載せたい親ブランチのスナップショット」をレビューするためのもの。

#### いつ PR を出すか

- **全子の完了を待つ必要はない。** 親上で統合・検証が済んだ塊を、段階的に `dev` へ載せてよい。
- 次のいずれかを満たすタイミングで出す。
  - 親にマージ済みの子のまとまりが、単体で `dev` に入れてよい状態になった。
  - チームで「いったん `dev` に統合する」と合意したマイルストーン（例: Project Foundation 完了時点）。
- **未マージの子 PR や作業中の子ブランチが残っていても**、親 → `dev` の PR は作成できる。それらの変更は **親に入るまで `dev` には入らない**。
- 親 → `dev` をマージした **あとでも**、別の子は引き続き親へ PR できる。再度 `dev` に載せるときは、**更新された親** で **もう一度** 親 → `dev` の PR を出す（2回目以降は差分が前回マージ分より後ろだけになる）。

#### 作成手順（GitHub/Bitbucket等）

1. ローカルで親ブランチをチェックアウトし、リモートと同期する。

   ```bash
   git fetch origin
   git checkout feature/parent-example
   git pull origin feature/parent-example
   ```

2. **`dev` を親に取り込み、競合を解消する**（PR 前または PR 更新時）。

   ```bash
   git merge origin/dev
   # またはチーム方針で git rebase origin/dev
   git push origin feature/parent-example
   ```

   `dev` が進んだまま親だけ古いと、PR マージ時やマージ後に `dev` 側で競合が増える。親 → `dev` の PR を出す前に、親を `dev` 最新に近づけておく。

3. GitHub/Bitbucket等 で PR を作成する。
   - **Source branch**: 親作業ブランチ（例: `feature/phase1`）
   - **Destination branch**: `dev`
   - **Compare / 差分の見方**: `dev...親`（three-dot）。「`dev` から見て、親が追加している変更」が PR の範囲になる。

4. コミット履歴・ファイル差分を確認する。

   ```bash
   git log --oneline origin/dev..HEAD
   git diff --stat origin/dev...HEAD
   ```

5. PR 本文は [PRテンプレート（親 → dev）](#prテンプレート親--dev) を使う。取り込み済みの **子 PR 一覧**（マージ済み / オープン / 未着手）を必ず書く。

6. レビュー・マージ後、必要なら親ブランチを `dev` 最新に同期し、残タスクの子作業を続ける。

#### 複数子が同時期に親へ集まるときの書き方

- **マージ済み子**: タイトル・PR リンク（または GitHub/Bitbucket等 PR ID）・担当範囲の一行要約。
- **オープン子 PR**: 親には未反映だが進行中である旨。`dev` には入らないことを明記。
- **未着手の子**: 親ブランチ上の予定タスクとして列挙（実装計画・worklog へのリンク可）。
- **親 → `dev` で意図的に含めないもの**: まだ子に分割していない作業、次マイルストーン分などを「未対応事項」に書く。

これにより、レビュアは「今回 `dev` に入る塊」と「まだ親だけ / これから子で入る塊」を区別できる。

#### タイトル・説明の例

```text
[feat] Phase1（親統合）— Project Foundation までを dev へ反映
```

- 括弧内は **親テーマ**。末尾は **今回 `dev` に載せる到達点**（全 Phase1 完了ではないことが分かるようにする）。

#### 注意（子 PR との混同を避ける）

| 誤り                              | 正しい操作                                 |
| --------------------------------- | ------------------------------------------ |
| 子ブランチ → `dev` に PR          | 子 → **親** に PR。`dev` へは **親** 経由  |
| 親...子 の差分で親 → `dev` を説明 | 親 → `dev` の説明は **`dev...親`**         |
| 子 PR 本文に親全体の完了を書く    | 子は子の範囲のみ。親全体は親 → `dev` PR で |

## dev / main へのマージ方針

| 変更の種類                       | 分岐元                                 | マージ先                     |
| -------------------------------- | -------------------------------------- | ---------------------------- |
| 通常の機能・修正・ドキュメント等 | `dev`                                  | `dev`                        |
| 子作業ブランチ（チーム並行）     | 親作業ブランチ                         | 親作業ブランチ               |
| 親作業ブランチ（チーム並行）     | `dev`                                  | `dev`                        |
| 本番緊急の `hotfix/`             | `main`（または合意されたリリース基点） | `main` と `dev`              |
| リリース反映                     | —                                      | 人間が `dev` → `main` を実施 |

エージェントは **`dev` → `main` のマージや本番反映を独断で行わない**。

## Codex が作業する場合の追加ルール

- 作業前に **現在のブランチ名** と **追跡ブランチ** を確認する。子作業ブランチかどうかはスラッシュの数では判断せず、作業ログ、PR説明、またはユーザー指示に書かれた親ブランチとマージ先で確認する。
- `main` / `dev` への直接コミット・直接 push はしない。
- 子作業ブランチでは、**親 → `dev` の PR を勝手に作成しない**。子の完了は親への PR までとし、親から `dev` への PR は人間または明示指示がある場合のみ提案する（手順・テンプレートは [親作業ブランチ → dev](#親作業ブランチ--dev)）。
- 親ブランチの有無・最新化が不明なときは、子の実装前にユーザーへ確認する。
- 作業ブランチ名が命名規約に合わない場合は、実装・コミット提案の前にユーザーへ確認する。新規ブランチ名に `yyyyMMdd` を付けない（[命名規約の変更（2026-06-02）](#命名規約の変更2026-06-02)）。
- コミットメッセージを提案するときは Conventional Commits 形式（要約は日本語）にする。
- PR 説明を作るときは、上記「Pull Request 作成ルール」の項目を含める。
- コミットや PR を作成する前に `./scripts/agent-check.sh`（利用可能な場合）で自己確認する。
- 破壊的操作・secrets・認証・認可・外部送信先など重大領域に関係する変更は、人間確認なしに進めない。
