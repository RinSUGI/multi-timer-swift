# 永続化・データモデル

## この文書で決めること

タイマーの保存形式、保存場所、正規化、書き込みの直列化、破損対応、レガシー移行、保存タイミングを定義する。

一次情報源: `_archive/multi-timer-mac/src/main/timer-storage.ts`。

## 保存場所

- 既存版の保存先: `~/Library/Application Support/multi-timer/timer.json`（Electron の `userData` = アプリ名 `multi-timer` のディレクトリ）。
- Swift 版の保存先はアプリケーションサポート配下の `timer.json` とする。既存利用者のデータを引き継ぐかどうかで、ディレクトリ名の選択が変わる（[Open Questions](#open-questions) の OQ-04 を参照）。
- App Sandbox は有効にしない前提とする。有効にすると保存先がコンテナ（`~/Library/Containers/<バンドルID>/` 配下）に変わり、既存データの引き継ぎ（OQ-04）と本書のパス前提が成立しなくなる。Mac App Store 配布は対象外のため、無効で問題ない。

## 保存形式

ファイルは次の JSON。

```json
{
  "timers": [
    {
      "id": "3de4d565-415d-4b89-8f6f-4634adb9907c",
      "title": "作業タイマー",
      "configuredMs": 1500000
    }
  ]
}
```

- `id`: タイマーの一意識別子（更新・削除の対象特定に使う）。
- `title`: タイトル（最大 50 文字）。
- `configuredMs`: 設定時間（ミリ秒、最大 `99:59:59`）。

保存するのはこの 3 項目のみである。残り時間・実行中・黄色状態は保存しない。したがって再起動時、各タイマーは「残り時間 = 設定時間・非実行・白」で復元される。

## 定数

| 定数           | 値                                     | 意味             |
| -------------- | -------------------------------------- | ---------------- |
| 最大タイトル長 | 50 文字                                | 超過分は切り詰め |
| 最大設定時間   | `(99*3600 + 59*60 + 59) * 1000` ミリ秒 | `99:59:59`       |
| 最大タイマー数 | 12                                     | 超過分は切り捨て |

- これらは UI 側と共有する単一の定義とする（[10-requirements/non-functional.md](../10-requirements/non-functional.md) の NFR-08 を参照）。

## 正規化

1 件のタイマーを正規化する規則（`normalizeTimer` 相当）。

- 入力がオブジェクトでなければ、その要素は無効として捨てる（`null` を返す）。
- `id`: 非空文字列ならそのまま。そうでなければ新規 UUID を採番する。
- `title`: 文字列なら先頭 50 文字に切り詰め。そうでなければ空文字。
- `configuredMs`: 有限数なら `floor` して `[0, 最大設定時間]` にクランプ。そうでなければ 0。

## パースと移行（`parseTimers` 相当）

- 正常形式: `{ timers: [...] }`。各要素を正規化し、無効な要素（`null`）を除外し、先頭 12 件に切り詰める。
- レガシー形式: `{ title, configuredMs }` の単一オブジェクト。1 件の配列へ移行する。
- 「移行が発生した」とみなす条件（`migrated = true`）。
  - 要素数が 12 を超えていた。
  - `id` を持たない要素があり、採番で補った。
  - レガシー形式だった。
- 移行が発生した場合、正規化後の内容でファイルを書き戻す。

## 破損対応

読み込み時の異常は次のように扱う（アプリが起動不能にならないことを最優先とする。NFR-05）。

- ファイルが存在しない（ENOENT 相当）: 空配列を返す。エラーとしない。
- 読み込み自体の失敗（存在するが読めない等）: ログに記録し、空配列を返す。
- JSON パース失敗（クラッシュ・電源断で書き込み途中になった等）: 破損ファイルを退避してから空配列を返す。
  - 退避先: 同ディレクトリの `timer.corrupt-<タイムスタンプ>.json`。
  - 退避に失敗してもログに記録し、空配列で継続する。

## 書き込みの直列化

- 保存・削除・読み込みは直列に実行する。
- 理由: 複数の保存が「読み込み → 配列更新 → 書き込み」の 3 ステップで同時に走ると、互いに上書き・混入して壊れた JSON を生む。
- Swift 版では、シリアルな `DispatchQueue` または `actor` で全ファイル操作を直列化する（[40-architecture/technology-choices.md](../40-architecture/technology-choices.md) を参照）。

## 保存操作の意味

- 保存（`saveTimer` 相当）: 入力を正規化し、現在のファイルを読み、`id` 一致があれば更新、無ければ末尾に追加し、12 件に切り詰めて書き込む。
- 削除（`deleteTimer` 相当）: ファイルを読み、`id` 一致を除外し、変化があれば書き込む（変化が無ければ何もしない）。

## 保存タイミング

| きっかけ             | タイミング                                          |
| -------------------- | --------------------------------------------------- |
| タイトル入力         | 入力が止まってから 300ms 後に 1 回（デバウンス）    |
| セグメント編集の確定 | 確定時（既存はタイトルと同じ 300ms デバウンス経路） |
| Clear                | 実行時（既存はタイトルと同じ 300ms デバウンス経路） |
| タイマー追加         | 追加時に即インサート                                |
| タイマー削除         | 削除時に即削除                                      |

- デバウンスは、素早い連続入力のたびにファイル書き込みが走るのを防ぐ。
- タイマー削除時は、保留中のデバウンス保存をキャンセルしてから削除する。

## Open Questions

- OQ-04 既存 Electron 版のデータ（`~/Library/Application Support/multi-timer/timer.json`）を Swift 版へ引き継ぐか。引き継ぐ場合は同じディレクトリ名・ファイル形式を用いる。引き継がない場合は新規ディレクトリで開始する。既存の JSON 形式はそのまま読めるため、引き継ぎは容易。
  - 決定: 引き継ぐ。同じ `~/Library/Application Support/multi-timer/timer.json` を読み書きする。形式・正規化規則が同一のため追加実装はほぼ無く、既存利用者がタイマーを再設定せずに移行できる。

- OQ-05 セグメント編集確定時と Clear 時の保存を、既存同様に 300ms デバウンスとするか、即時保存とするか。挙動差は小さいが仕様として明示しておく。
  - 決定: タイトル入力は既存どおり 300ms デバウンスとし、セグメント編集の確定と Clear は即時保存へ変更する。確定・クリアは単発操作でファイル書き込みの連発が起きにくく、即時保存のほうが実装が単純で、直後にアプリを終了しても取りこぼさない。
